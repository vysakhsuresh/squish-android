# Text, titles, captions and stickers

> **Historical. 28 September 2026, and almost none of it is true any more.**
> This was the audit against CapCut that the build plan came out of, written
> before batches B1–B16 existed. It is kept because the *reasoning* in it is
> what `docs/ROADMAP.md` was built from, and because a few of its "gap" entries
> are still open — but every statement about what the app does or does not have
> is seven batches out of date. For what is built, read `ARCHITECTURE.md` §5;
> for what is unseen on a device, `CLAUDE.md` and `docs/DEVICE_FINDINGS.md`.


Read-only audit of the text/caption/sticker surface (CaptionsPanel, StickersPanel, TextStyle, CaptionRenderer, SquishTextOverlay, LiveCaptionOverlay, plus the view-model, autosave, preview engine, export and timeline code they depend on). Nothing was built or run; every bug below is traced to lines, and effects that need a device are labelled as such.

The rendering core is sound: one renderer paints captions for preview and export, the preview layer is value-driven (no pipeline rebuild per keystroke), stickers reuse the caption path, autosave round-trips every text field, and SRT import/export is forgiving. What is missing is almost the entire CapCut text *workflow*: there is no on-canvas editing at all (no drag, pinch, rotate, tap-to-select, handles), no keyboard-first add-text flow, no free placement for captions (Top/Middle/Bottom only, x locked), no adjustable stroke/shadow/background/opacity/alignment/spacing/rotation, a 7-swatch colour row, six system fonts, six combined in/out animations with a fixed 450 ms and no loop, no apply-to-all, no text-to-speech, emoji-only stickers, and a selected text clip on the strip that opens nothing.

Traced defects, most serious first: auto-captions are placed in source time and ignore the head clip's trim/position/speed (and only the first file is analysed); captions over a retimed clip preview at the wrong moment because shiftedInto uses a constant offset while the surface runs in source time; text edits from the panels (Remove, Clear all, Add line, typing, SRT import, auto-caption, pin) bypass the undo stack while the same delete from the strip is undoable; re-running auto-captions duplicates every line; every keystroke/style change re-seeks every audio player via setTimeline→primeAudio; captions are also drawn on PiP surfaces in the preview but not in the export; dragging a caption to the left edge shortens it; adding text with the playhead at the end places it after the last frame; Cut is enabled for a selected caption but splits the video instead; caption rows are not keyed so focus can land in another caption; an off-centre custom crop lays captions out differently in preview and export; captions over a gap vanish silently.

One risk I could not settle by reading: SquishTextOverlay (media/SquishTextOverlay.kt:43-57) compares raw per-item presentationTimeUs against timeline-time startMs/endMs, while ClipTransformEffect in the same per-item effect list deliberately latches its own origin because Media3 has offered both item-relative and composition-relative times. If Transformer hands item-relative times, every caption on any clip but the first renders at the wrong moment in the export; only a device export settles it, and it should be the first thing checked on the phone.

## gap · critical · L — No on-canvas text or sticker editing (drag, pinch-scale, rotate, tap-to-select, handles)

**Detail:** Text position is chosen from three chips (Top/Middle/Bottom, CaptionsPanel.kt:320-322, 371-379) with x locked to 0.5; stickers are moved with two unit-less sliders (StickersPanel.kt:140-148). There is no rotation field on TextOverlayItem at all (EditorModels.kt:79-107), so nothing can be rotated in preview or export. The preview's only picture overlays are the crop overlays (EditorScreen.kt:291-313); tapping the picture toggles play (TimelinePreview.kt:204-210). No selection box is drawn for the selected text item.

**CapCut:** Every text and sticker on the preview has a bounding box with four corner handles: delete (top-left), duplicate (top-right), edit text (bottom-left), scale+rotate (bottom-right). One finger drags, pinch scales, two fingers rotate, snap guides show at the frame centre and edges, tap selects the item and its lane clip, double-tap opens the keyboard. This is where most of CapCut's text work happens.

**Evidence:** CaptionsPanel.kt:320-322 (Place chips), StickersPanel.kt:140-148 (sliders), EditorModels.kt:79-107 (no rotation/opacity fields), TimelinePreview.kt:204-210 (tap = play), EditorScreen.kt:291-313 (pictureOverlay has only crop overlays)

## bug · high · M — Auto-captions are placed in source-file time, ignoring the head clip's trim, position and speed; only the first file is analysed

**Verified:** true

**Verification:** The core defect is real and traceable. generateCaptions (EditorViewModel.kt:1332-1417) decodes only `current.sourceUri` from file offset 0 (PcmDecoder.decodeMono takes no start offset), segments in file time, and at 1390-1396 writes `segment.startMs/endMs` straight into TextOverlayItem. TextOverlayItem times are timeline time by contract: EditorModels.kt:101-104 says the track is "stored in timeline time, matching startMs and endMs"; PreviewEngine.kt:462-466 converts them timeline->source with `shiftedInto` (EditorModels.kt:122-131, delta = sourceInMs - timelineStartMs); and the export OverlayEffect (VideoProcessor.kt:564-569 -> SquishTextOverlay.getBitmap) is fed composition presentation time, which is timeline time (CompositionFactory addGap honours timelineStartMs). No caller converts the segments through the clip that carries that file, and clips added via the add-clips path (EditorViewModel.kt:1207-1224) with other URIs are never analysed at all. The panel label at CaptionsPanel.kt:171 ("Auto-caption this clip") and 143 ("No speech found in this clip") reinforce the single-clip framing.

However, the reviewer's headline scenario is wrong as stated.
